### Allowed Category values (use only these)
| Category | Use when |
|----------|----------|
| **Functional** | Happy path, core requirement behavior, filter/search flows, state changes |
| **Negative** | Invalid input, error paths, no-results, rejected operations |
| **Boundary** | Min/max limits, empty/null, off-by-one, whitespace-only, edge thresholds |
| **Security** | Injection, authz, XSS, unsafe input handling |
| **Validation** | Input format rules, clarification-heavy UX (empty keyword, no-results messaging) |
| **Performance** | Latency, rapid/resubmit, load, sync timing |

Do **not** use: `Core requirement tests`, `Requirement clarification tests`, `Security/non-functional recommendations`, or any other label.

### Category mapping (common mistakes to avoid)
- Core/happy-path requirement coverage → **Functional**
- No-results / empty input / format checks → **Validation** or **Negative** (by intent)
- Limit/threshold/whitespace boundary → **Boundary**
- Injection / unsafe payloads → **Security**
- Rapid submit / sync wait / timing → **Performance** or **Functional** (not Security unless threat-based)

### Priority rules
- Assign **one** priority per test case: P0, P1, P2, or P3 only.
- Do **not** write compound priorities (e.g. `P0 (P1 for variants)`).
- If variants need different priorities, split into **separate test cases** (e.g. TC-011a P0, TC-011b P1) or use a parameterized table where **each row maps to one scenario and one priority**.
- Inherit priority from linked scenario when possible; document in Generation Summary if overridden.

### Primary classification vs assertion tags
- **Primary classification** — exactly one per test; drives mutually exclusive summary counts:
  - **Requirement-derived** — pass/fail criteria explicitly supported by requirement or scenario
  - **Needs clarification** — blocked or outcome undefined until spec is confirmed
  - **Recommendation** — best practice / security / UX suggestion not stated in requirement
- **Assertion tags** — list every label that applies (including the primary). Tags overlap across tests; tag summary counts are **non-mutually-exclusive** and may sum to more than total test cases.

### Steps and assumptions
- Every step must be actionable. If a step cannot run until spec is clarified (e.g. sync SLA undefined), mark the step **Blocked: Needs clarification** and list in Self-check — do not leave vague waits ("wait for sync") without criteria.
- Never turn an assumption, best practice, or inferred behavior into an Expected Result unless explicitly stated in the requirement or scenario, or labeled Needs clarification / Recommendation.
- Do not invent UI messages, session behavior, matching rules (case sensitivity, partial match), or filter AND/OR logic unless requirement-backed or flagged Needs clarification.

### Duplication and parameterization
- Detect duplicate/overlapping test cases before finalizing. Prefer parameterized cases for same behavior with multiple input values.
- **Near-duplicates are not allowed** (e.g. two TCs for rapid/overlapping submissions) — merge, cross-reference, or split by distinct observable outcome.
- Do not duplicate security-focused cases as functional cases (keep Functional vs Security separation clear).
