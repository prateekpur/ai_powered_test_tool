### Category (test type — exactly one)
| Category | Use when |
|----------|----------|
| **Functional** | Happy path, state changes, duplicate-submission and concurrent flows |
| **Negative** | Invalid input, rejected operations, error paths |
| **Boundary** | At-limit behavior when limit is **defined** in requirement |
| **Security** | Auth, tampering, injection with plausible attack surface |
| **Validation** | Input format rules with defined constraints |
| **Performance** | Latency, throughput, SLA — **not** double-submit or race conditions |

### Test objective (exactly one — orthogonal to category)
Calculation | Eligibility | State management | Concurrency | Duplicate submission consistency | Authorization | Data integrity | Abuse prevention | Input validation | Persistence | Payment integrity | Error handling | Observability

**Mapping examples:**
- **Sequential** duplicate apply (same session, apply twice in order, no parallel overlap) → Objective: **Duplicate submission consistency** — **NOT** Concurrency
- **Concurrent** duplicate apply (double-click, two tabs, parallel/overlapping requests) → Objective: **Concurrency**
- Cart change after coupon applied → Objective: **Eligibility** or **State management**
- Percentage discount math → Objective: **Calculation**
- User A modifies User B's order → Objective: **Authorization**; Category: **Security**

**Terminology:** Do **not** use "idempotency" in titles, business rules, or objectives unless the requirement **explicitly** defines an idempotency policy. Until then use **duplicate submission consistency** (same input re-submitted → consistent outcome per requirement or gap).

### Severity (impact-based — avoid Critical inflation)
| Situation | Severity |
|-----------|----------|
| Arbitrary discount / financial loss / wrong payment amount | Critical |
| Authorization bypass / usage-limit bypass | Critical |
| Duplicate coupon application causing double discount | Critical |
| Expired/invalid coupon accepted **with** discount applied | Critical or Major |
| Expired/invalid coupon accepted **without** discount | Major |
| Wrong or generic error message only | Minor |
| Case sensitivity / label copy / max-length UX | Minor |

### Business rule deduplication (strict — most important quality gate)

**One executable test per business rule.** A business rule is the single verifiable policy under test, e.g.:
- BR-DUP-SUBMIT — Re-applying the same valid coupon does not increase discount (use **duplicate submission consistency** wording unless requirement says "idempotent")
- BR-REJECT-EXPIRED — Expired coupon is rejected and no discount applied
- BR-MIN-CART — Cart below minimum after apply invalidates or removes coupon

Before writing tests:
1. List all distinct business rules implied by requirements (typically 12–20 for a feature this size)
2. Assign **exactly one** TC per rule in the executable suite
3. Use a **matrix inside that TC** for multiple inputs/outcomes of the **same** rule

**FAIL deduplication** (do not generate separate TCs) when tests differ only by:
- Wording of the same outcome ("discount unchanged" vs "response unchanged" vs "zero monetary delta")
- Same action replayed with same preconditions (sequential apply twice = double-click apply = "duplicate apply" unless mechanisms differ materially)
- Same rejection case already covered in a matrix row of another TC

**Allowed second test for duplicate submission** only when mechanisms differ:
- **Sequential** re-apply → one TC, Objective: Duplicate submission consistency
- **Concurrent** (double-click vs multi-tab) → at most one TC **each**, Objective: Concurrency
- Do **not** label sequential duplicate submit as Concurrency

**Cap duplicate-apply coverage** in executable suite:
- At most **one** TC for sequential/repeated apply (Objective: Duplicate submission consistency)
- At most **one** TC per **concurrent** mechanism (double-click, multi-tab — Objective: Concurrency)
- Do **not** add TCs that re-verify "discount unchanged" under the same mechanism

If a matrix row in TC-010 already covers "duplicate apply → rejected/no extra discount", do **not** add TC-005, TC-011, TC-017 for the same rule.

### Executable test rules
- Do **not** put undefined-rule tests here — use Section 2 (Requirement Gaps)
- Do **not** put security-hardening not in requirements here — use Section 3 (Recommended Tests)
- **Parameterized/matrix:** consolidate near-duplicates (e.g. cart-before/after minimum) into one TC with a table of Initial → Modified → Expected
- **Calculation:** distinguish discount calculation from final order total (tax/shipping recalculation)
- **Time boundaries:** express as T = expiry ± ε per contract; do not assume midnight inclusive without requirement
- **Rate limits:** only executable if N requests / T seconds is defined; otherwise → Requirement Gap
- **Cross-references:** every "see TC-xxx" must point to an existing ID in this output
