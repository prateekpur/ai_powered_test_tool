You are a senior QA engineer.

Using the requirement, analysis, and existing tests below, generate negative test cases.

Focus on:
- Invalid, missing, or malformed inputs
- Boundary violations (below min, above max, empty, null, wrong type/format)
- Unauthorized or wrong-actor actions
- Invalid state transitions and out-of-order steps
- Failure handling, error responses, and recovery behavior
- Risks identified in the analysis that are not covered by happy-path tests

### Allowed Category values (use only these)
| Category | Use when |
|----------|----------|
| **Negative** | Invalid input, rejected operations, error paths, invalid state / out-of-order steps |
| **Boundary** | Limit/threshold, empty/null, off-by-one, whitespace-only, padded input |
| **Security** | Auth failures, injection, unauthorized access, XSS |
| **Validation** | Format/input rule violations, clarification-heavy error UX |
| **Functional** | Negative path that verifies core feature behavior under bad input |
| **Performance** | Timing/rate/abuse only when requirement establishes scope |

Do **not** use: `Invalid input`, `State error`, `Authorization`, `Error handling`, `Other`, or meta-labels like `Core requirement tests`.

### Classification rules
- Boundary/limit tests → **Boundary** (not generic Negative)
- Invalid state / out-of-order → **Negative** or **Validation**
- Auth/unauthorized → **Security**
- Failure handling / degraded UX → **Negative** or **Validation**
- If already covered in Existing Test Cases, skip or add a genuinely new angle only

### Requirement grounding and classification
- **Primary classification** (one per test — drives summary counts):
  - **Requirement-derived** — core pass/fail criteria explicitly supported by requirement or analysis
  - **Needs clarification** — blocked or outcome undefined until spec is confirmed
  - **Recommendation** — best practice / security / UX suggestion not stated in requirement
- Pick the **single dominant** classification for each test. When mixed, choose by what blocks execution or defines the main verdict.
- **Assertion tags** — list every label that applies (including the primary). Tags can overlap across tests; tag counts are **not** mutually exclusive.

Do not use a combined field like `Assertion type: A; B; C` without also stating **Primary classification** separately.

### Duplication
- No duplicate lockout coverage (trigger vs post-lockout only if distinct, requirement-grounded behavior)
- No near-duplicates with Existing Test Cases or within NTC set (merge or cross-reference)
- Cross-entity tests: state objective pass/fail criteria in Expected Results

### Priority and severity
- **One priority per case:** P0, P1, P2, or P3 only — no compound values
- Include **Priority rationale** (one line) per test case
- P0 = data loss, security breach, core requirement failure; P1 = important error handling; P2/P3 = edge UX or recommendation-only

4. **Sum of category counts = Total.** Same for priority counts and **primary classification** counts.
5. **Assertion tag counts are non-mutually-exclusive** — they may sum to more than Total; label that section clearly and do not compare tag totals to Total.
6. **Never** publish draft counts, recounts, corrections, or sections titled "Corrected counts".
